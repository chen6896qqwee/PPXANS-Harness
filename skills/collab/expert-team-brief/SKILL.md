# 专家班组简报

## 适用
准备把任务派给一个或多个专家/专家班组时, 组装他们各自要看的任务描述。

## 流程

1. **先给背景, 再给任务**。子 agent 看不到你的对话历史 —— 它只知道你写给它的这几百字。缺背景 → 它自己脑补一个 (通常不对)。
2. **一份简报的六段** (顺序固定):
   1. 背景: 这是什么项目/系统, 当前处在什么状态 (含关键文件路径)
   2. 目标: 这次要产出什么 (具体到交付物形态)
   3. 约束: 不能做什么、必须遵守什么 (技术栈、目录、风格、时间)
   4. 已知信息: 前面已经查清/试过的东西 (**特别是试过不行的**, 防止它重走一遍)
   5. 交付格式: 输出的结构与粒度 (要清单?要表格?要代码?要多长)
   6. 验收标准: 什么样的产出算合格
3. **按角色裁剪内容, 不裁剪事实**。给代码专家和给商业顾问的详略应不同, 但**事实必须一致** —— 不同角色拿到互相矛盾的事实会产出无法调和的结论。
4. **视角要差异化且具体**。写"聚焦并发与边界条件", 不要写"仔细一点"。视角的作用是对抗同质失败: 同一个模型同上下文必然给出同一个答案。
5. **一次派发只给一个明确目标**。含多个目标的简报会让子 agent 只做最容易的那一个。
6. **附上可复现的最小上下文**: 具体文件路径、具体命令、具体数据片段。让它能立刻动手, 而不是先花轮次找东西。
7. **回收前想清楚**: 这份简报派出去, 我期望拿回来的具体是什么? 说不出来就不要派。

## 反合理化
- "任务很简单不用写背景" → 越简单的任务, 子 agent 越会用自己的默认假设补齐背景, 而你不知道它假设了什么。
- "把整段对话复制给它" → 对话里一半是过程噪音。只给结论、约束与路径。
- "多给点信息总没错" → 无关信息会分散注意力并抬高成本。给"做这件事所需的全部", 不是"我知道的全部"。
- "验收标准让它自己定" → 它定的标准会倾向于它容易做到的事。
- "已排除项不用写, 它自己会判断" → 不写它就会重试, 你会为同一个失败付两次钱。

## 验证
- [ ] 六段齐全 (背景/目标/约束/已知/格式/验收)
- [ ] 含具体路径、命令或数据片段, 可直接动手
- [ ] 已排除项已写入
- [ ] 视角具体且与其他角色有区分
- [ ] 单一明确目标
- [ ] 明确的交付格式与验收标准
- [ ] 各角色收到的事实互相一致
