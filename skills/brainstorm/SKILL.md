## 流程

**核心铁律: 在告知用户意图并获得明确批准前, 不得写代码/建项目/采取实施行动。门禁随任务规模伸缩, 审批从不伸缩。**

1. **分类**（先向用户说出口，便于推翻）：
   - **探测 (Spike)**：可行性问题（"能做到吗/是否可能"）→ 只给答案，不留代码
   - **受限 (Bounded)**：对**已存在**代码的小改动（新标志/小端点/单文件修复）→ 聊天里 2-3 句设计 + 批准
   - **架构级 (Architectural)**：新项目/新子系统/重构接口 → 完整流程（提问→方案→设计→规格→计划）
2. **提问**（一次一个，只问真正影响执行的）：
   - 目标：最终要达到什么效果？成功标准是什么？
   - 范围：涉及哪些文件/服务/数据？哪些明确不做？
   - 约束：有现成流程要遵守吗？有历史决策吗？
3. **呈现方案**：2-3 个方案 + 权衡 + 你的推荐。包含：方法、涉及文件、测试方式。
4. **等批准**：停下来，等明确的"是"。不要一边展示一边开干。

**判定陷阱**：
- "我熟悉这类应用" ≠ 受限，受限衡量的是仓库里**有没有现成流程**，不是你的熟悉度
- 想选更轻路径来跳过工作 = 疑虑信号，走更重路径
- 中途发现隐藏复杂度 → 升级路径，停下说明，**永不降级**

## 反合理化

| 借口 | 现实 |
|------|------|
| "这太简单不需要设计" | 简单意味着简短设计，不是无设计。聊天两句话 + 审批 |
| "设计很明显，我边读边开始" | 门禁是审批，不是设计长度。先呈现，再等"是" |
| "他批准了探测，后续改动也算" | 每个任务有自己的分类和审批 |
| "用户没反对就是默认同意" | 沉默不是批准。没有明确的"是"就不要动手 |

## 验证

- [ ] 已向用户说明任务分类（探测/受限/架构级）
- [ ] 已呈现设计或方案（含涉及文件和测试方式）
- [ ] 已获得用户明确批准
- [ ] 无批准时未产生任何代码/文件改动
