# 长任务跟踪

## 适用
任务跨多个回合/多天, 或中途被打断需要续跑。也用于会话开始时的"接上上次"。

## 流程

1. **开场先回忆, 不要重新开始**: 用 memory_search / replay_session 找上次状态; 有 goal_board 先读板。把上次的结论当作既成事实, 不要重新论证一遍。
2. **维护四件事** (缺一不可):
   - 已完成: 产出物路径 + 验证结论 (不是"做过了")
   - 进行中: 当前卡在哪一步, 卡的具体原因
   - 已排除: 试过但不可行的方案 + 为什么不行 (防止下一轮又绕回来)
   - 下一步: 一个具体的、不用再决策的动作
3. **把状态写进持久层**: 关键结论用 memory_add 落长期记忆; 任务级状态用 goal_board 落看板。只写在回复里 = 下轮就没了。
4. **不要重复验证**: 上次已经验证过的结论, 本次直接引用并注明"上轮已验证"。重复跑同一验证是长任务最大的浪费。
5. **每轮结束前更新看板**, 而不是等用户问进度。
6. **卡住时明确升级**: 卡超过两轮就写清"卡在哪、需要什么、可选哪几条路", 交给用户拍板, 不要静默重试。

## 反合理化
- "我先看看代码再决定" → 先回忆状态。没看状态就重读全仓是最常见的浪费。
- "这个之前试过了吧, 再试一次" → 试过就写进已排除项。没写说明记录没做, 现在补上。
- "用户没问进度就不用报" → 长任务不主动同步状态, 用户会以为你没动。
- "重跑一遍验证更保险" → 重复验证不增加信息, 只消耗时间与预算。

## 验证
- [ ] 本轮开始时读过上次状态 (会话/记忆/看板)
- [ ] 四条状态项都有内容, 且"下一步"是具体动作
- [ ] 关键结论已落持久层 (memory_add / goal_board)
- [ ] 已排除项有理由, 不只是"不行"
- [ ] 没重复执行上轮已验证的步骤
