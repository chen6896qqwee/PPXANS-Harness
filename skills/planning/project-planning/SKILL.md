# 项目排期

## 适用
已有任务清单, 需要回答"什么时候能做完、先后顺序、卡点在哪"。

## 流程

1. **前置检查**: 没有任务拆解结果先做拆解 (task-decomposition)。排期不能代替拆解。
2. **画依赖图**: 节点 = 任务, 边 = 依赖。找出关键路径 (最长依赖链) —— 项目的完成时间由关键路径决定, 不由任务总和工作量决定。
3. **确定瓶颈资源**: 谁/什么是只能串行使用的 (你本人、某个审批人、某台机器)。瓶颈的利用率决定整体吞吐, 优先为瓶颈排期。
4. **估工只给区间**: 乐观/常见/悲观三档。只给一个数字的估算是假精度。区间宽说明任务还没拆清楚, 回去拆。
5. **加缓冲只加在关键路径**: 每个非关键任务的缓冲会被后续吸收, 加在关键路径末端才有意义。一般留总量的 20%~30%。
6. **标外部依赖**: 需要别人给的东西 (审批、素材、数据、账号) 单独列, 标最晚需要时间与催办点。
7. **输出**: 里程碑 (带日期区间) → 关键路径 → 瓶颈与对策 → 外部依赖与最晚时间 → 风险最高的三个任务。

## 反合理化
- "先把时间加总就是工期" → 加总忽略依赖与并行, 几乎总是高估。
- "每步都加缓冲更保险" → 缓冲分散等于没有缓冲, 而且会让所有人低估紧迫度。
- "估不准就先给个日期" → 给不出区间的日期是承诺不是估算, 会变成后续所有争执的源头。
- "关键路径等排完再看" → 关键路径就是排期本身, 不是事后分析。

## 验证
- [ ] 关键路径已识别并有日期
- [ ] 估算以区间给出 (乐观/常见/悲观)
- [ ] 瓶颈资源已识别并有对策
- [ ] 外部依赖列了最晚需要时间
- [ ] 缓冲只在关键路径上, 且标明了占比
