# 代码审查循环

## 适用
审查一段代码、一个文件、或一批改动 (diff/PR)。也可作为"实施 → 只读审查 → 修复 → 复审"循环里审查者的作业规范。

## 流程

1. **先建立全貌**: 读改动涉及的文件 + 它们的直接调用方。只看 diff 不看上下文, 是漏掉接口破坏类问题的原因。
2. **按顺序过五类问题** (顺序固定, 防止被细节带偏):
   - 正确性: 边界条件、异常路径、空值与类型、并发/竞态
   - 接口契约: 调用方是否仍然成立、返回形状是否变化、向后兼容
   - 安全: 注入、密钥硬编码、路径穿越、越权、危险默认值
   - 资源: 泄漏 (句柄/定时器/监听)、无界增长、超时缺失
   - 可维护性: 重复逻辑、命名误导、注释与行为不符
3. **每条发现三要素**: 严重度 + 位置 (文件:行) + 为什么是问题。缺"为什么"的发现会被当成风格偏好忽略。
4. **严重度只用三档**: Critical (会导致错误/失败/安全问题) / Important (质量缺陷或明确风险) / Minor (小改进)。不用"建议考虑"这类模糊档。
5. **只报告不修改** (审查者角色下)。发现问题不等于有权改: 修改需要回到实施者, 由实施者保持上下文完整地修。
6. **给可执行结论**: 每条问题写"改成什么"的最小方向, 而不是让实施者猜。
7. **收尾**: 输出发现清单 → 通过与否的明确判断 → 未决项的处置建议 (谁裁)。

## 反合理化
- "代码能跑就是对的" → 能跑只覆盖了走过的路径。边界与异常路径才是缺陷藏身处。
- "这是风格问题不重要" → 分不清"风格"与"误导"就会漏掉真正的可维护性问题。命名误导是 Important 不是 Minor。
- "审查太慢, 挑几个重点看看" → 抽着看等于没看。要么完整过一遍, 要么明确说明只覆盖了哪部分。
- "发现的问题我直接改了更快" → 审查者改了, 实施者就不知道自己错在哪, 同样的错会再犯。

## 验证
- [ ] 读了改动文件及其调用方, 不只读 diff
- [ ] 五类问题逐类过了一遍 (包括确认无问题的类别)
- [ ] 每条发现带严重度 + 位置 + 理由
- [ ] 严重度只用三档
- [ ] 每条问题给了修改方向
- [ ] 给出了明确的通过/不通过判断
