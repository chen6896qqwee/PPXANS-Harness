# 测试先行

## 适用
新增功能、修缺陷、重构 —— 任何"做完要能证明做对了"的改动。
不适用: 一次性探索脚本 (但探索结论转成正式代码时仍要补测试)。

## 流程

1. **先写失败用例**。修缺陷时: 用例必须能在当前代码上失败 (真复现), 失败不了说明你没找对根因。新功能: 用例描述期望行为, 现在跑必然失败。
2. **把复现证据贴出来**: 具体的命令 + 失败输出。没跑过的"应该会失败"不算复现。
3. **改动最小化**: 只改让用例通过所必需的部分。顺手重构、顺手优化一律延后, 否则用例通过时你分不清是哪处改动起的作用。
4. **跑全量回归**, 不只是新用例。新用例绿而别处红, 等于没修好。
5. **补边界用例**: 空输入、极值、异常路径、并发/重复调用。happy path 一个用例就够, 边界才是缺陷聚集区。
6. **覆盖"不变量"而非"实现细节"**。测试应断言行为与契约; 断言内部实现细节的测试会在重构时集体失效, 那不是保护而是负债。
7. **记录验证结论**: 命令 + 通过数 + 失败数。数字要真实, 不允许"应该都过了"。

## 反合理化
- "改动很小不用测" → 改动越小越容易漏掉调用方。跑一次回归成本很低。
- "这个 bug 我看一眼就知道原因" → 知道原因不等于知道怎么修对。先写失败用例把它钉住。
- "测试跑太久了, 只跑相关文件" → 可以只跑相关文件做快速迭代, 但提交前必须跑全量一次。
- "顺手把这个也改了" → 混在一起的改动, 出问题时要二分定位, 代价远大于省下的那点时间。
- "断言具体返回值更严格" → 严不严格看它是否表达契约。钉死实现细节会让重构寸步难行。

## 验证
- [ ] 有先失败后通过的用例, 且贴了失败输出
- [ ] 改动限定在让用例通过的最小范围
- [ ] 跑了全量回归, 给出了真实的通过/失败数
- [ ] 补了边界用例 (空/极值/异常/重复)
- [ ] 断言针对行为契约而非实现细节
