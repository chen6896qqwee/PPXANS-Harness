# 仓库上手

## 适用
第一次接触一个代码库, 需要在不改任何东西的前提下说清"它是什么、怎么跑、从哪改"。

## 流程

1. **先看清单文件** (package.json / pyproject / go.mod / Cargo.toml): 名称、版本、依赖数、scripts 入口。依赖数量本身就是重要信息 —— 零依赖项目的改动风险结构与重依赖项目完全不同。
2. **画目录地图, 只到两级**。标出: 入口、核心逻辑、测试、配置、数据。超过两级的目录先不管。
3. **找入口**: Web 项目看 bin/ 与 server 启动脚本; CLI 看 main/bin 字段; 库看 exports/main。从入口顺着调用链走一层, 建立主干印象。
4. **用 repo_map / search_files 定位关键符号** (不要靠 list_dir + 逐个 read_file 硬翻, 那是无底洞)。
5. **读测试当文档**: 测试文件往往比 README 更真实地描述行为与边界。先看测试文件名的分布, 就知道作者在意什么。
6. **确认运行方式**: 有没有 build 步骤、需不需要外部服务、跑测试的命令。**真的跑一次测试** —— 拿到基线 (多少通过、多少失败), 这是后续任何改动的对照物。
7. **挖出隐含约定**: 命名规则、错误处理风格、日志方式、注释语言。这些不在文档里, 但违反它们会让改动显得格格不入。
8. **输出上手笔记**: 一句话定位 → 关键路径 (入口→核心→存储) → 运行/测试命令 → 隐含约定 → 三个"改这里要小心"的点。

## 反合理化
- "先把所有文件读一遍" → 读不完, 也记不住。从入口顺链路走一层的信息密度最高。
- "README 说了就够了" → README 常与现实脱节。至少跑一次测试或启动一次。
- "测试跑不跑无所谓, 我又不改" → 基线就是你的望远镜。不知道原本红绿状态, 后面所有判断都是猜。
- "目录结构看不懂, 我随便猜一下用途" → 猜出来的用途会污染后续所有结论。标"未确认"更好。

## 验证
- [ ] 说清了项目定位与运行方式
- [ ] 标出了入口与主干调用链
- [ ] 实际跑过一次测试/启动, 拿到了通过/失败基线
- [ ] 列出了 3 条以上隐含约定
- [ ] 标出了高风险改动点
- [ ] 全程未修改任何文件 (只读上手)
