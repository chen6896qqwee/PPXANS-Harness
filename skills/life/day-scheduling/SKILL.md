# 日程编排

## 适用
用户给出一堆要做的事 (待办、会议、截止日期), 需要落成具体时间块。
不适用: 已经有明确日历排好的, 只要提醒的 (直接用 add_schedule)。

## 流程

1. **先取真实当下时间**: 调 `get_time`。绝不假设今天是哪天, 也不要按记忆里的日期推算。跨时区必须先问清用户在哪个时区。
2. **把所有输入摊平成一维清单**: 每条含 事件名 / 固定或弹性 / 预计时长 / 截止时间 / 依赖谁。缺项不要用"大概半小时"填, 直接标 `[时长待定]` 并列进待确认。
3. **算可用时间总量**: 清醒时段减去固定会议, 再减去通勤/用餐这些硬占用。得出的数字要写出来, 后面所有排布都受它约束。
4. **按后果排优先级**, 不是按紧急感: ①有外部截止且不可延期的 ②卡住别人的 (依赖方在等) ③自己推进的 ④可延期的。同档内先排耗时短的。
5. **排时间块并留缓冲**: 缓冲占总可用时间的 15% 到 25%。不给缓冲的排法等于排一个必然崩的计划。
6. **冲突显式暴露**: 放不下就说放不下, 给出取舍选项 (砍哪个 / 顺延到哪天 / 压缩到多长), 不要硬塞进同一天。用户有权决定砍什么, 你只负责算清楚代价。
7. **要提醒的落成定时任务**: 用 `add_schedule`。落库前把「什么时候 + 提醒什么」原样复述一遍确认, 时间写绝对日期而不是"明天"。
8. **输出结构**: 时间块表 (开始-结束 / 事项 / 类型) → 没排进去的清单及原因 → 冲突与取舍建议 → 需要用户拍板的项。

## 反合理化
- "今天应该是周三" → 调 `get_time`。日期错了整张表都废。
- "这个会议默认一小时" → 用户没说就标待定, 编出来的时长会让后面全线漂移。
- "挤一挤总能塞下" → 排进去但做不完的计划, 比明确说"今天做不完"更糟。算总量, 说结论。
- "缓冲不用留, 满了效率高" → 没有缓冲的计划遇到第一个意外就整体崩塌。15% 是下限。
- "用户看起来很急, 那就先排急的" → 紧急感是主观的, 后果才是客观的。按后果排, 再把判断依据讲给用户听。
- "我先排好再问他要不要调" → 砍掉哪件事是用户的决定, 不是你的。你给选项。

## 验证
- [ ] 用了 `get_time` 取的真实时间, 时区已确认
- [ ] 可用时间总量已算出并写出数字
- [ ] 每条事项都有时长依据, 缺时长的已标待定而非编造
- [ ] 缓冲占比落在 15% 到 25%
- [ ] 排不下的已明说, 并给了取舍选项
- [ ] 定时任务的时间是绝对日期, 且已复述确认
- [ ] 输出含"没排进去的"和"需用户拍板的"
