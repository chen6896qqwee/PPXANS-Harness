# plan — 计划拆解

**输入**：一个目标 + 现状约束（已有什么、不能动什么、截止到什么时候）。
**输出**：终局定义 → 有序步骤表（含依赖/可回滚性）→ 关键路径 → 检查点位置。

## 流程

1. **定终局**：写下"做完时什么样"（**可观察的终态**），不是"要做什么"。终局不可观察就没法验收。
2. **倒推步骤**：从终态往回拆，每步输出必须是下一步的输入。
3. **标注**：每步标 ① 依赖 ② 可回滚性 ③ 预计触碰的文件/系统。
4. **找关键路径**：哪一步最可能卡住？先做它（风险前置，而不是按顺序从第一步磨）。
5. **设检查点**：在**不可逆动作之前**插一个"停下来确认"，写清确认什么、谁来拍板。
6. **分层**：超过 7 步就分组（阶段一/二/三），每组自带一个可验证的中间产物。
7. **产出**：有序步骤表 + 关键路径 + 检查点位置 + 每步的验收方式。

## 反合理化

- "边做边想"——不可逆的部分不允许边做边想。
- "先全部做完再测"——每步都应可独立验证，否则失败时无法二分定位是哪步引入的。
- "步骤越多越专业"——超过 7 步就该分层，堆步骤是在用篇幅冒充严谨。
- "这步肯定没问题"——"肯定"不是验证手段；凡是标了"肯定"的步骤，补一句怎么证伪它。

## 边界与例外

- **不要用本技能的场景**：单步就能完成的任务（直接做）；还在探索该不该做（先做可行性判断，不是排步骤）；线上故障（先止血，事后复盘再排整改计划）。
- **依赖未知**：若某步的前置依赖还没确认（例如"等三方接口文档"），把它标成 **阻塞项**并单列，不要假装它能排进序列 —— 未知依赖会让整条关键路径失效。
- **步骤之间耦合到拆不开**：说明这不是一个计划而是一个设计问题，先回到方案层面（选型/架构）再排步骤。
- **计划执行中被打断**：回来时先重跑第 1 步（终局是否变了），终局没变才接着走 —— 大多数"计划失效"其实是终局被改了但没人说。

## 示例（形态参考）

> 目标："把一个 33 模块的 Node 项目依赖环清掉。"
> 终局：`node scripts/arch-guard.js` 输出「依赖环: 0」。
> 步骤：① 写守卫脚本量出环 → ② 定位每条环上的具体 import → ③ 按"常量下沉 / 模块归位 / 入口移出"分类 → ④ 逐个修 → ⑤ 冻结剩余越层进基线 → ⑥ 接进 CI。
> 关键路径：②（改错地方会把一个环拆成两个）。
> 检查点：④ 之前 —— 移动文件会改相对路径，先确认引用点已全量列出。

## 验证

完成后必须给出：① 步骤表（含依赖与可回滚性）；② 关键路径；③ 每个不可逆动作前的检查点；④ 终局的可观察判据。
有阻塞项时必须单列，不得混进步骤表假装可执行。
