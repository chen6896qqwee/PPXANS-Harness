# debug — 根因排障

**输入**：一条报错 / 一个异常行为 / 一个失败的测试。
**输出**：最小复现命令 → `文件:行号` 根因 → 新增的回归测试 → 全量回归结果。

## 流程

1. **读完整报错**：全文读，包括栈与 code（`ERR_*`），别只看第一行。最后一行往往是果，第一行才是因。
2. **稳定复现**：写出**最小复现命令**。不能复现就先想办法复现，别改代码。
3. **二分定位**：把链路切成两半，确认问题在哪半，重复到最小单元。别用"我觉得"。
4. **根因陈述**：用一句话说清"为什么"，并**指出它在哪一行**。说不出行号就是还没定位到根因。
5. **先写回归**：修之前先加一个**能失败的测试**，再改到它通过。测试一开始就是绿的，说明它没抓住这个 bug。
6. **验证修复**：跑全量回归，确认没有连带破坏。
7. **记一笔**：同一个坑第二次遇到就该沉淀（经验/注释/文档），别让第三次还靠猜。

## 反合理化

- "先改改看"——猜测式修改会把真正的根因埋得更深（改完"不报错了"往往只是把症状挪了地方）。
- "这个报错以前见过"——相似报错 ≠ 同一根因。
- "加了 try/catch 就不报错了"——那是掩盖，不是修复。
- "改完好了就行"——没写回归，下次还会犯。
- "环境问题吧"——在证明它不是环境问题之前，这句话等于没说。

## 边界与例外

- **不要用本技能的场景**：还没确定预期行为的"不对劲"（先问清应该是什么样，否则无从判断是不是 bug）；线上正在烧的故障（先止血/回滚，再按本流程复盘）。
- **复现不了**：不要靠猜去改。改为加日志/加观测把链路照亮；间歇性问题优先怀疑**时序与并发**（竞态、未 await 的 Promise、缓存失效时机），而不是逻辑。
- **改一个地方冒出另一个错**：通常是同一个根因的多处症状，回到第 4 步重新定位，不要逐个症状打地鼠。
- **测试本来就红**：先确认基线（改动之前是不是就红）—— 否则会把别人的 bug 算到自己头上，然后在错误方向上越改越远。
- **定位到行号但说不出"为什么"**：说明只找到了现象位置，未找到机制。回到第 3 步继续二分，不要急于改。

## 示例（形态参考）

> 报错：`Error: Cannot find module './postcondition.js'`
> 最小复现：`node -e "import('./src/core/policy.js')"`
> 二分：文件确实存在 → 说明不是缺失而是路径解析问题 → 定位到 `src/core/policy.js:12` 的 `from "../verify/postcondition.js"`（模块已移动，相对路径失效）。
> 回归测试：断言 `import('./src/core/policy.js')` 不抛错。
> 全量：1554 项测试，0 失败。

## 验证

必须提供：① 最小复现命令与原始报错；② 定位到的 `文件:行号` 根因（含"为什么"）；③ 新增的回归测试（且证明它修复前是红的）；④ 全量回归结果。
若最终没能定位到根因，如实说"未定位"，并给出已排除的范围 —— **不允许用"修好了"掩盖"不知道为什么好了"**。
