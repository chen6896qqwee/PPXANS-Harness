# 技能创作

## 适用
一次任务做成功了, 想把这套方法固化下来下次直接用; 或要新建/改进一个技能。
不适用: 一次性的、不可复现的运气。

## 流程

1. **先自问"值得固化吗"**: 这套方法是否满足 ①可复现 (不是靠特定运气) ②跨任务有用 (至少会再遇到两次) ③有明确判据 (做没做对能判断)。三条不满足就别建 —— 幻觉技能比没有技能更糟。
2. **定触发**: description 要写清"什么情况下用它"。**这是技能被检索到的唯一依据** —— 用任务场景的词, 不要用抽象的能力名。"处理多来源材料冲突时的合并流程" 好过 "知识整合能力"。
3. **写正文三段 (必备)**:
   - `## 流程`: 逐步工作流, 每步可执行、有检查点。步骤间有依赖要说明。
   - `## 反合理化`: 常见偷懒借口 + 反驳。**这一段的密度决定技能的实际约束力** —— 只写流程的技能会被"这次情况特殊"绕过。
   - `## 验证`: 完成后必须提供的证据 (勾选清单)。没有验证段的技能无法自检。
4. **正文必须引用真实工具名**。技能的价值在于可执行; 不引用具体工具的技能只是文章。
5. **写进去的东西必须能被验证**: 每条流程都问"怎么知道这步做对了?"。答不上来的步骤要删除或改写。
6. **落盘与验证**: 写到 `skills/<domain>/<name>/SKILL.md` (name 用英文横线命名)。写完后**用 SkillLoader 确认能被发现、frontmatter 能解析、章节能按名读取**——不能发现的技能等于不存在。
7. **改进旧技能时**: 改动后必须保持"验证"段不被删除, 且正文不得比原版更短 (防退化闸门会拦)。

## 反合理化
- "这次成功了, 赶紧记下来" → 先确认是方法有效还是运气好。把运气写成技能会在别处翻车。
- "description 写宽一点能命中更多场景" → 过宽的 description 会被大量无关任务误命中, 效果是噪音。
- "反合理化那段是给人看的, 不用认真写" → 它是技能唯一的抗绕过机制。没它, 流程段在第一次"情况特殊"时就会失效。
- "先写正文, 验证回头补" → 验证是技能的验收面, 后补的验证往往是走过场。
- "技能写长一点更全面" → 长不等于有用。命名与步骤被稀释后更难被检索与执行。

## 验证
- [ ] 通过了"可复现/跨任务有用/有判据"三项检查
- [ ] description 含明确触发场景词
- [ ] 流程 / 反合理化 / 验证 三段齐全且非空壳
- [ ] 正文引用了真实工具名
- [ ] 每条流程步骤都有对应的判断依据
- [ ] 落盘后确认 SkillLoader 能发现, 章节能读取
- [ ] 若是升级旧技能: 验证段保留且正文未缩水
