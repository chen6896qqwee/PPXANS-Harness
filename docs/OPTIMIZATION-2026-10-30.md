# 架构评审与热路径优化（2026-10-30 / v3.5.0）

> 📌 **历史评审留痕**（2026-10-31 加注）：本文写作时自称 v3.5.0, 当前源码版本已是 v4.0.0 —— 版本数字以 package.json 与 [ARCHITECTURE-CURRENT.md](./ARCHITECTURE-CURRENT.md) 为准, 本文只作评审与优化过程存档。
>
> 本文回答两件事：**① 这套系统现在长什么样、钱花在哪；② 在不动语义的前提下，把每轮对话的固定开销砍掉了多少、怎么砍的、怎么证明没砍坏。**
> 权威架构快照仍是 [ARCHITECTURE-CURRENT.md](./ARCHITECTURE-CURRENT.md)（§1–§9 描述 v3.5.0 现状，§10 是本轮实测记录）。本文不重写它，只做**评审 + 优化留痕**，并记下这轮**没有做**的结构性问题，避免下次重新发现一遍。

## 0. 一句话结论

系统的分层是清楚的（通道 → HTTP → 协议队列 → Agent 内核 → LLM 底座），真正的浪费不在设计而在**热路径的重复同步 I/O**：每轮对话的内核固定开销里约 95% 是文件系统调用，其中单是"每轮重扫技能目录"就占了 1/3。本轮把其中 5 处按"校验代替重读"的思路改掉，**同一脚本同机 A/B：每轮内核固定开销 26.67ms → 16.51ms（−38.1%，中位 −40.1%），单轮 readdir 88 次 → 0 次**（各分项见 §5 与 ARCHITECTURE-CURRENT §10.3）；语义由既有 1,800+ 用例、漂移守卫、双进程回归和新增加的回守卫共同兜住。

## 2. 架构快照（读出来的骨架）

### 2.1 分层与入口

```
通道层    public/(Web UI, 零构建) · cli.js · 飞书 · 微信 · log · workspace
   │ HTTP: 静态资源 / /api/* / SSE / /message/stream       （channels/*）
   ▼
接入层    channels/http.js —— 鉴权 / 限幅 / 路由 / MCP over HTTP
   ▼
协议层    protocol/ —— SQ 提交队列 + EQ 事件流(WAL) · Session→Task→Turn 投影
   ▼
内核层    PPXAgent（src/agent/）
          装配五阶段: 插件容器 → 服务绑定 → ANS 接线 → 引擎(模式/军团) → 启动动作
          主链: chat/chatStream → mode → policy 工具循环 → 回退链
          旁挂: 记忆五层 / 权限与钩子 / 进化体系 / 自愈
   ▼
底座      llm/ —— 自研 OpenAI 兼容客户端（多 provider、思考强度注入、重试、fence）
```

**装配五阶段**（`src/agent/index.js` 构造器，顺序即依赖顺序）：
1. `_initPluginContainer` —— `Context` 容器 `provide/consume`，内置插件按依赖序注册（bus/healer/persona/facts/experience/sessions/memory/llm/traces/audit/scheduler/tools/modes/playbook + v3 五插件），用户插件目录可覆盖任一实现；
2. `_bindServices` —— consume 成公开属性 + 权限能力门 + **零侵入包装所有 provider 的 usage 记账**；
3. `_wireANS` —— 免疫闸门 / Reward 闭环 / 排泄自治；
4. `_initEngines` —— 模式注册表、军团（spawn_agent 多进程 + DAG）、专家班组；
5. `_initServices/_initStartup` —— 会话恢复、每日进化循环、审批面、MCP 连接。

### 2.2 一轮对话"付钱"的地方（本文的靶子）

`chat()` 每轮固定做这些事，**与用户问了什么、模型回了什么无关**：

| 阶段 | 每轮发生的事 | 本轮优化 |
|---|---|---|
| 开轮 | SQ 提交 op + EQ 推 `TURN_STARTED`（WAL 落盘） | — |
| 装配 system prompt | `_context()`：persona/画像/经验/技能目录/计划/playbook/记忆检索… | **OPT-1**（技能目录扫描）、**OPT-4**（画像正文读） |
| 调模型 | 路由 + 回退（stub 下为 0） | — |
| 落轮 | `_pushTurn`：会话事件 append ×2~4 + flush（文件锁 + 尾读 + 追加写） | **OPT-2**（尾读按批次复用） |
| 记忆 | `recordTurn`：状态文件原子写 + 事实/经验写入 + 压缩检查 | **OPT-3**（纯计数状态写节流） |
| 收尾 | 生命周期 tick、进化 tick、总线事件、usage | — |

## 4. 发现（按影响排序）

### P0 · 已修：热路径上的重复读取/重复写入
1. **技能目录每轮全量重扫**（80×readdir + 67×stat ≈ 5.7ms/轮）。技能目录一天也不会变几次，却按"轮"付钱。
2. **画像正文每轮整文件读**（2 次 ≈1.2ms/轮）。画像一天变一次。
3. **会话 append 每条都读磁盘末行**（一次落轮 2~4 条，重复读同一份末行 ≈1ms/轮）。这条读本来就是"乐观预读"，权威判定在 flush 锁内。
4. **记忆状态文件每轮全量原子写**（锁 + 写 + rename ≈1.7ms/轮），其中每轮唯一真正变化的是 `turnCount` 计数。
5. **flush 锁内对同一文件重复尾读**（锁内 `_diskMaxSeq` 与随后的"追加 or 整写"判定各读一次）。

### P1 · 未修：同步 I/O 就是并发天花板
内核热路径几乎全是**同步** `fs.*Sync`（全仓 324 处同步调用）。单线程事件循环被同步 I/O 占住，20 并发 stub 压测 p50 360ms、p99 378ms（顺序跑是 ~17ms/轮）。这不是 bug（零依赖 + 同步锁换来的"简单正确"），但它是**吞吐上限**：
- 多会话/多 agent/Web 多标签页并发时，其他请求要排队等 I/O；
- 军团 worker 是独立进程，不受影响，但主进程的并行会话受影响。

**建议（需独立窗口，不要顺手改）**：把"每轮都要写"的落盘改成**异步批量提交 + 进程内串行队列**（append-only 先入内存队列，flush 用 `fs.promises`，读路径保持同步不受影响），或至少把 `_pushTurn`/`recordTurn` 的写盘挪到 `setImmediate` 之后。收益是并发延迟，风险是"崩溃时最后几条未落盘"——需要和现有"会话即唯一事实源"的承诺对齐后再动。

### P1 · 未修：镜像副本双维护（语义有闸门，性能没有）
`skills/ppx-memory/scripts/` 与 `skills/ppx-selfheal/scripts/` 是随技能分发的"可拷出独立版"，靠 `test/skill-memory-drift.test.js` 守"src 符号 ⊆ 副本符号 + 行为标记"。本轮 mem-opt 已把 OPT-2/OPT-3 同步进 `session.js`/`memory-ticker.js` 副本（无新符号），但**这条通道是手工的**：闸门只查符号与标记，查不出"同一份实现两套性能/两套边角逻辑"。
**建议**：给漂移守卫加一条"性能关键实现片段必须逐字一致"的白名单校验，或把这些内核文件改成"单一实现 + 生成副本"（脚本化同步，CI 校验副本 = 生成结果）。

### P2 · 维护面（记录在案，本轮不动）
| 问题 | 现状 | 影响 |
|---|---|---|
| 巨型文件 | `src/agent/index.js` ~2.1k 行、`src/channels/http.js` ~1.6k 行 | 改动冲突面大、审阅成本高 |
| 脚本 sprawl | `scripts/` 43 个入口，其中压测/评测类 8 个（bench/benchmark/memory-benchmark/audit-bench/nightly-bench/bench-store/taskbench/expert-drill） | 新人不知道跑哪个；口径易分叉 |
| 空 catch | 117 处 `catch {}`（多数带注释，`silent-catch-guard` 在管） | 真正吞错的会被淹没 |
| 配置备份堆积 | `config/ppx.json.bak-<ts>` 已积 3 份，无轮转 | 目录越来越脏 |
| 分层债 | `plugin/` 同时装 DI 容器（应 L0）与装配器（L4），`agent → plugin` 是 arch-guard 基线里唯一存量越层 | 不许再增加，清它要先把容器下沉到 core |

### P2 · 文档漂移（本轮已修，并补了闸门盲区）
`README.md` 散文里的数字和实测对不上，而且**闸门的正则抓不到这些句式**（`PROSE_CHECKS` 只认特定写法，匹配不上就打印"未找到对应句式"然后放行）：
- `93 内置工具` → 实测 96；`暴露 86 工具` / `86 工具全量暴露` → 实测 `/mcp` 暴露 118；
- `全量测试 1764 项` → 实测 1,790（本轮后 1,806）；

### 伴随约束（改这几处必须同时守住的契约）
1. **镜像副本漂移守卫**（`test/skill-memory-drift.test.js`）：`src` 声明符号集必须 ⊆ `skills/ppx-memory/scripts/*` 副本；副本只能 `node:` 或 `./` 导入（可整目录拷走）。本轮改动刻意**不新增符号**，因此副本只需同步内部逻辑。

## 9. 同日第二轮：工具循环加固（成功率 / 稳定性 / 判等正确性）

> §1–§8 那轮省的是"每轮固定开销"（I/O），本轮动的是**循环怎么结束、怎么并发、怎么判重复**。
> 三者都在 `src/core/policy.js` 一个文件里，改动面窄，但每一个都直接改行为 —— 所以全部配了新守卫。

### 9.1 三处问题（都是读代码读出来的，不是拍脑袋）

| # | 现状 | 后果 | 判定依据 |
|---|---|---|---|
| **H-1** | 跑满 `max_tool_rounds`（默认 8）直接 `return "[皮皮虾] 工具调用轮次过多, 已停止。"` | 前 7 轮读的文件、改的代码、跑的测试**全部作废**；用户拿到零信息，还以为啥也没干。这是"任务成功率"上最贵的一行代码 —— 它把"做了一半"变成"什么都没做" | `src/core/policy.js` 循环出口只有一句常量 |
| **H-2** | 同一轮的 N 个 `tool_calls` 无条件 `Promise.all` 全并发 | 模型一次吐 20 个 `run_command` 就是 20 个 shell 同时 spawn。军团侧早有 `max_concurrent_agents` 背压（`orchestrator/governor.js`），工具侧一个没有 —— 稳定性只靠模型自觉 | 全仓 `semaphore/pool` 只出现在 orchestrator |
| **H-3** | 重复调用签名 = `JSON.stringify(args).slice(0,120)` | 键序不同即视为"新调用"：模型用 `{path,limit}` 和 `{limit,path}` 重发同一请求，重复计数器纹丝不动，熔断比设定晚好几轮；`services/triage.js` 的 LOOP 归因同样漏判 | `JSON.stringify` 跟随属性插入序 |

### 9.2 改法

- **H-1 轮次耗尽强制收口**：循环结束后补一次 **`tools: []` 的调用**，把 `EXHAUSTED_FINALIZE_PROMPT`（已做什么/没做完什么/下一步）追加成 user 消息，让模型基于已有轨迹收口；返回体末尾强制加诚实标注（`⚠️ 工具轮次上限已用尽 (N 轮 / M 次调用, 其中 K 次成功)`）。
  四条边界，缺一条都不收口：**无工具轨迹**（没东西可总结，白花一次调用）、**用户中断**、**预算已耗尽**（不点单）、**收口调用失败或空回复**（回落原硬停止文案，不假装成功）。
  开关 `agent.exhausted_finalize`（默认 `true`）。
- **H-2 同轮并发上限**：`mapBounded(items, cap, fn)` 保序有界并发（下标对齐输入，`collect()` 仍按 `tool_calls` 顺序回传/配对，`tool_call_id` 配对不乱）。`agent.max_parallel_tools` 默认 **4**（与 `legion.max_concurrent_per_call` 同量级），`0` = 不限（旧行为），调用数未超限时仍走原全并发路径（零额外开销）。
- **H-3 稳定签名**：新增 `src/utils/canonical.js` 的 `stableJson(value, maxLen)`（键名升序、深度上限防环、数组顺序保留 —— 数组顺序是语义不能归一）。`policy.recordTurn` 与 `services/triage.sig` 同步换用，**两处共用一份实现**（上一轮刚批评过"镜像双维护"）。

### 9.3 A/B 实证（同一探针、同机、旧文件 vs 新文件）

探针直接 import 目标 `policy.js`，在临时目录里用备份的旧文件跑同一组用例：

| 观测点 | 旧 | 新 |
|---|---|---|
| 8 个同轮调用的并发峰值（`max_parallel_tools: 3`） | **8** | **3** |
| 换键序重发同一调用 → 是否触发重复方向盘 | **false** | **true** |
| 4 轮耗尽后的返回 | `[皮皮虾] 工具调用轮次过多, 已停止。` | 收口正文 + `⚠️ 工具轮次上限已用尽 (4 轮 / 4 次…)` |
| 该场景的 LLM 调用次数 | 4 | 5（多出的 1 次就是收口） |

### 9.4 代价与不做的部分

- **多一次 LLM 调用**：只在"确实执行过工具 + 没收口过 + 没被中断/预算拦"时发生，正好是"钱已经花了、只差一句话"的场景；不想要就 `exhausted_finalize: false`。

- **没有改的**：§7 的 P1（落轮写盘异步化）、镜像副本生成化仍然是下一轮的事，本轮不碰。

### 9.6 顺带修掉的偶发红（不是本轮引入）

全量回归第 3 次跑出 1 个失败，与被改代码无关：`test/skills-scan-cache.test.js` 的
`扫描缓存: 稳态 readdir 从 80/次 降到 0` 断言"sleep 250ms 后必须重扫全树"，实测 readdir = 0。

## 10. 同日第三轮：把工具 schema 的钱收回来（成本维度）

> 前两轮都盯着"每轮要跑的 I/O"（§1–§8）和"循环怎么结束"（§9）。这一轮盯的是**每轮都要发的
> token**：工具 schema。这是全仓最贵的一项固定开销，而且它长什么样从来没被质疑过。

### 10.1 量化：96 个工具 = 11.2k tok/请求，占固定开销 77%

`node scripts/ctx-profile.js` 实测（空会话、无历史、默认配置）：

| 项 | tok/请求 |
|---|---|
| 工具 schema（97 个） | **12,591** |
| `_context()` 全部注入 | 1,882 |
| **合计固定开销** | **14,447** |

再看 `data/logs/traces/*.jsonl`（2026-10-23~10-30，327 条真实轨迹）的工具调用分布：

```
http_request 32 · fetch_page 17 · run_command 14 · list_dir 12 · write_file 10 · read_file 9
code_act 6 · get_time 4 · … 其余各 1~2 次; 出现过的一共约 30 个工具
```

**96 个工具里只有约 30 个被调用过，前 6 个占 2/3 调用量。** 剩下 60 多个工具（team_room_*、
expert_pack_*、persona_*、git_*、self_*、vad_detect…）从头到尾没被用过一次，却每轮都在付 schema 钱。

### 10.2 更难看的是：机制早就写好了，只是没人接

`ToolCatalog.setExposure()` / `hiddenFromLLM()` （2026-10-05 实现）注释里白纸黑字写着
"名字仍出现在 system 静态区【按需工具】名单里（见 agent prompts）" —— 而 `prompts.js`
里**根本没有那一段**。全仓 `setExposure` 零调用方。这是典型的"完整实现 + 半截接线"：
读文档的人以为有这个能力，读代码的人发现它从没生效过。

### 10.3 本轮做的三件事

1. **接线**（不改默认行为）
   - `agent._applyToolExposure()`：读 `config.agent.tool_exposure`（`"all"` 默认 / `"core"` / 自定义数组），
     启动与 `reloadSettings` 各应用一次（改配置不用重启）。
   - `prompts._toolsPrompt()`：新增【按需工具】段，只在收窄时非空；名单恒升序（前缀缓存契约），
     超出字符预算截断并指路 `list_capabilities`；纳入 `_fitSystemSections` 的裁剪顺序。
2. **给一条真路**：新增 `tool_schema(name)` 工具 —— 名字 → 完整 JSON Schema，支持逗号分隔多个。
   没有它，"按需工具"就是"名字可见、参数全靠猜"，比全量下发更糟。它自己在核心名单里，
   自定义名单也会被强制并入（`META_TOOLS_ALWAYS`）。
3. **瘦身**：删掉工具描述里"逐条复述参数语义"的重复部分（参数表里已经写了），
   spawn_agent 描述 103→53 tok、code_run 87→57、skill_import 98→82、vad_detect 62→52、
   team_room_open 106→78。新增 `tool_schema` 的 ~100 tok 正好被这些抵掉，**默认预算没涨**。

### 10.5 边界（诚实说明）

- **默认没改**：`tool_exposure` 默认仍是 `"all"`。收窄会不会降低工具调用准确率，需要真模型 A/B

## 11. 同日第四轮：并发到底卡在哪（测量 + 逐项证否，本轮几乎没改运行时）

> §7 的 P1 写着"把落轮写盘异步化，这是并发吞吐的唯一上限"。这个判断方向对，但**没有指明是哪一段**。
> 照着它动手，很容易花半天改错地方 —— 本轮先做实验，把"该动"和"不该动"分清楚。
> 结论先说：**瓶颈是 `memory.recordTurn` 整体（占并发场景 71%），不是任何一个单独的文件写入**；
> 而拆开逐个优化每一个子项都只有个位数收益。所以这轮交付的是**测量能力 + 证否清单**，不是半成品改动。

### 11.1 先修测量工具：原来的 bench 根本没测并发

`scripts/bench.js` 前两项（并发调用 / 长会话）都跑在 **default 会话**上。而 `agent.chat()`
对同一 sessionKey 有 `_withSessionLock` 串行化 —— 那是设计（防历史交错/记忆双写），不是能力上限。
于是旧 bench 量到的 800ms p50，量的是"排队"，**真正的并发能力被完全掩盖**。

本轮新增第 (3) 项：**隔离会话并发** —— N 个不同 sessionKey 同时跑，与"同样多请求串行跑"比总耗时，
得到 `slowdown`（1.00 = 完全串行，越接近 1/N 越好）。

```
── (3) 隔离会话并发 (20 会话 × 3 轮 = 60 请求) ──
  并发 2008ms (p50 669ms) | 串行 2295ms (38.3ms/请求)
  并发度 slowdown = 0.87  (1.00 = 完全串行; 越接近 0.05 越好; 失败 0)
  ⚠ 不同会话之间没有有效并行 —— 内核热路径的同步 fs I/O 占住了事件循环
```

**20 个不同会话、60 个请求，和串行跑一样慢。** 那 0.13 的重叠只是 `await` 处让出的一点点调度。

### 11.2 逐项证否（同一探针，20 会话 × 3 轮，只关一个变量）

| 关掉什么 | 并发总耗时 | 相对基线 | 结论 |
|---|---|---|---|
| 基线（全开） | 2344 ms | — | — |
| 事件流 + 工具轨迹写入 | 2312 ms | −1% | **不是它**（`appendFileSync` 小文件几乎不阻塞） |
| 画像正文读 `_readPersona` | 2379 ms | +1% | 不是它（OPT-4 缓存已生效） |
| `_context()` 整体 | 2382 ms | +2% | 不是它 |
| 文件锁轮询粒度 20ms → 4ms | 2418 ms | +3% | 不是它（冲突等待本来就不长） |
| `FactStore` 切 WAL 模式（追加事件代替全量写） | 2178 ms | −5% | 几乎不是它 |
| `session` 落盘 `_flush` | 1876 ms | **−20%** | 有份，但不是主因 |
| **`memory.recordTurn` 整体** | **677 ms** | **−71%** | **就是它** |
| └ 只关 `factStore.addMemory` | 1655 ms | −29% | 内部多个子项分摊，没有单点 |
| └ 只关 `_archiveTurnContext` | 1821 ms | −22% | 同上 |
| └ 只关 `_compactIfNeeded` | 1948 ms | −17% | 同上 |
| └ 只关 `factStore.add`（提炼路径） | 1599 ms | −32% | 同上 |

**关键读法**：关掉 `recordTurn` 整体省 71%，但关掉它内部任何单独一项只省 17%~32% ——
说明这份开销**不是某一行 I/O**，而是"每轮都要把记忆这一摊子完整跑一遍"的合计：
读全量 facts、索引、去重判定、衰减打分、追加归档、压缩检查，各自都不贵，加起来 12ms/轮 × 60 请求 = 720ms。

### 11.3 为什么不能像文档 §7 说的那样"简单异步化"

`withFileLock` 是**同步**锁，源码里有一条硬约束（注释写得很清楚，历史上真丢过用户数据）：

> 若 fn 是 async 函数，它返回的只是一个"刚开始执行"的 Promise —— 控制权在第一个 await 处
> 就交回事件循环，而那时临界区远未结束。于是锁在最需要它的地方静默失效。

把 `recordTurn` 改成 `await fs.promises.*` 必须同时把锁重写成异步锁，否则就是拿数据一致性换吞吐。
这不是"顺手改一下"，是独立工程，且需要配套的跨进程并发回归。

### 11.4 分层方案（按 ROI 排序，留给下一轮）

| 层 | 做法 | 预期 | 代价 |
|---|---|---|---|
| **L1 低风险** | `recordTurn` 里的**归档类**写入（`_archiveTurnContext` 的 turns.jsonl、`_compactIfNeeded` 的检查）改为"每 N 轮/每 5s 合并一次"，记忆检索仍读内存 | 乐观 −20%~30% | 崩溃丢最近几条**归档**（不是事实、不是会话，可从 events 重建） |
| **L2 中风险** | `FactStore` 写路径整体走 WAL + 定期 compact（机制已在，`config.memory.wal`），再把 WAL 追加从"每轮加锁"改成"进程内批量提交" | 乐观 −30%~40% | 需要把同步锁换成"批内合并 + 单次加锁"，跨进程语义要重验 |
| **L3 高风险** | 全部落盘异步化（含会话事实源） | 接近 N 路并行 | 必须重写 `withFileLock` 为异步锁 + 全套并发回归；语义上"崩溃丢最后几条会话"需要产品决策 |

**本轮没做 L1–L3 中的任何一个。** 理由：L1 的收益还没到"值得改数据落盘节奏"的程度（乐观 20%，
而 L2/L3 才是数量级变化），先做 L1 等于把回归风险摊在一个收益不足的方案上。

### 11.5 顺带修掉的两处文档漂移

- `docs/CONFIG.md`：`proactive.enabled` 默认值写 `false`，代码里是 `true`（2026-10 就改了，文档没跟）。
- `README.md` 目录树：`test/（1822 项）` → 实测 1830。

### 11.6 验证

- `node scripts/bench.js`：新增第 (3) 项正常输出，失败数计入退出码。
- 全量回归 / `npm run verify` 见本节提交时的记录（本轮未改运行时路径，仅改测量脚本与文档）。

### 11.7 顺带修掉一个真实损害成功率的阈值：探索熔断 3 轮 → 5 轮

`ToolLoopPolicy.recordTurn` 的探索熔断原本是"连续 **3** 轮都是只读工具 → 注入方向盘叫停"。
问题很直接：**"读 5 个文件再动手"是最常见的合法工作流**（分析仓库、排查 bug、写文档前收集素材），
而它会在第 3 轮被判定为空转，模型收到"请停止继续探测, 直接给出结论" —— 任务做一半被掐。

这个阈值当初设 3 是为了防"无目的乱翻"，但"防乱翻"这件事已经有独立的重复检测在管
（同工具+同参数命中 2 次即告警）。把两个不同性质的问题用同一个数字管，结果就是误伤正常探索。

改法：`DEFAULT_EXPLORE_BREAK` 3 → 5（`agent.explore_break_limit` 仍可调），文案同步改成
"连续 N 轮只有只读/查询工具, 未产生任何产出或修改"，避免用户以为自己在被指责。

- 新增用例：**连续 4 轮只读必须放行**（旧默认会在这轮叫停）
- 原有用例同步到 5 轮熔断
- 代价：真正无目的探索会多花 2 轮才被告警 —— 但那两轮的成本远低于"任务被做一半"的代价

### 11.8 L1 已实施：归档合批 + 压缩检查节流（−30% 并发总耗时）

按 §11.4 的分层，L1（低风险：只动**可重建**的归档写入）已落地。两处改动：

**① 压缩检查节流修复**（这不是优化，是 bug）
`_compactIfNeeded` 的 60s 节流读的是 `_lastCompactAt`，而它**只在真压缩完成后**才更新。
于是当天事件数没到压缩阈值（<50）的那些日子，每轮 `recordTurn` 都会 `replayDay` 把当天全部分片
读一遍再逐行解析 —— 节流形同虚设。新增独立的 `_lastCompactCheckAt`（检查节流 60s，
与压缩节流分开），压缩行为不变，只是把"每轮读盘"降到"每 60s 读一次"。

**② turns 归档合批**
`_archiveTurnContext` 原本每轮 `ensureDir` + `withFileLock` + `appendText`。turns 归档的唯一输入
就是 session 事件日志（丢了能重放），所以不必每轮付这三次系统调用：
- 入队 `_archiveQueue`，攒够 **5 条** 或距上次落盘超 **3s**（惰性判定）才真写；
- 真写时按文件分组，**一次锁 + 一次 append 写多行**；
- 三个强制收口点：**跨天** `_rollDay` / **读取** `turnArchive()` / **进程收口** `agent.shutdown()`。

首个轮次仍立即落盘（`_archiveFlushedAt` 初值 0 ⇒ 惰性超时对第一次必然成立），所以
"CLI 跑一轮就退出"这种最常见场景**零延迟**；合批只发生在 3 秒内的连续多轮。

镜像副本 `skills/ppx-memory/scripts/memory-ticker.js` 同步了同样的六处改动（漂移守卫 29/29）。

#### 实测（同机、同脚本）

| 指标 | 改前 | 改后 | 变化 |
|---|---|---|---|
| 单轮内核开销（同会话串行） | 38.3 ms | **31.6 ms** | **−17.5%** |
| 隔离会话并发 60 请求总耗时 | 2008 ms | **1530 ms** | **−23.8%** |
| 隔离会话 p50 | 669 ms | **507 ms** | −24.2% |
| 同会话并发压测 p50 | 804 ms | 666 ms | −17.2% |
| 并发度 slowdown | 0.87 | 0.81 | 略好，**没有质变** |

> **别把最后一行读成成功**：slowdown 0.81 意思是"20 个会话的 60 个请求仍然基本排队"。
> L1 减的是每轮的固定开销，不是让 I/O 变异步 —— 真正的并行要靠 L3（异步锁）。
> 这轮把单轮成本打下来 17%，等价于并发场景下每条请求占用的时间变短，排队总时长跟着降 24%。

#### 守卫（`test/turn-archive-batch-2026-10-30.test.js`，7 例）

- 合批期间文件不增长 → `flushTurnArchive()` 后一行不少（首轮 1 行 + 队列 3 行 = 4 行）
- 达到阈值 5 条自动落盘（6 轮 = 6 行，队列自动清空）
- `turnArchive()` 读取自动收口（不 flush 就读不到刚发生的轮次 = 会静默丢可见性）
- `agent.shutdown()` 必须收口（优雅退出不该丢归档）
- 压缩检查 6 轮只读一次当天事件；节流窗口过后必须重读（不是永久跳过）
- 空队列 flush 幂等


### 11.9 L2 已实施：锁内不重读 + 去重索引（收益比预期小，如实记录）

§11.4 把 L2 写成"FactStore 写路径批提交，乐观 −30%~40%"。实际做了两项更小的改动，
**收益只有 0.5%~7%** —— 下面连预期落空的原因一起写清楚。

#### 做了什么

**① 锁内 `_reload` 按磁盘签名跳过重读**
`add()` 在锁内调 `_reload()`，而它是 `readJson(全量 facts.json)` + `_stampProvenance(全量遍历)`
+ `rebuildIndex(全量重建 BM25 倒排)`。同进程刚写完时，内存就是那份内容，再解析一遍纯属浪费。
新增 `_diskSignature()`（`mtimeNs:size`，bigint stat 拿纳秒精度——毫秒精度在 NTFS 上判不出
"同毫秒两次不同写入"），签名未变直接返回内存态。`save()` / `_flushLocked()` 写盘后刷新签名，
否则自己的写会被当成"磁盘变了"而白读。

**② 去重走 O(1) 归一化键索引**
`add()` 去重原本对**全部 facts** 线性跑 `_normKey`（每条一次多次正则替换）。改为
`_byKey: Map<scope+归一化键, fact[]>`，与倒排索引同生命周期重建；命中后仍按 `status` 过滤，
与原线性 `find` 逐项同语义（含"跳过 deleted/archived"和"scope 精确匹配"）。

#### 实测（诚实版）

| 场景 | 改前 | 改后 | 变化 |
|---|---|---|---|
| `bench.js` 隔离会话（**空记忆库**） | 1530 ms | 1522 ms | **−0.5%（噪声内）** |
| 探针 20 会话 × 3 轮（**200 条**记忆库） | 1705 ms | 1588 ms | **−6.9%** |
| 同上（**800 条**） | 1653 ms | — | 与 200 条同量级（噪声内） |

**预期 −30%~40%，实际 −0.5%~7%。** 差在哪，用同一套探针拆开看：

| 关掉什么（200 条库基准 1705ms） | 耗时 | 占比 |
|---|---|---|
| 跳过 `_reload` 读盘 | 1660 ms | 7% |
| 跳过 `rebuildIndex` | 1761 ms | 1.6% |
| 跳过 `save()` 落盘 | 1515 ms | 11% |
| **跳过整个 `add()`** | **909 ms** | **47%** |

`add()` 的 47% 里，能被"批提交/WAL/索引"这类结构性优化吃掉的只有一小半；
剩下的（约 30%）是 `scrubPII` 的正则扫描、`_norm` / `_normKey` 的归一化、
`resolveWriteTier`、`withFileLock` 自身的五六个系统调用 —— 这些是**每轮都要做的纯 CPU/系统调用**，
除非改变"每轮都落一条记忆"这个产品行为，否则压不下去。

#### 所以没继续做 L2 的"批提交"部分

原计划里的"WAL 追加批提交"最多能吃到那 11% 落盘里的一部分。**收益不足以支撑**
"把记忆写入路径改成延迟提交"带来的语义风险（记忆是蒸馏产物、会被画像/检索消费，
延迟提交意味着读到旧值的时间窗）。**L3（异步锁）才是数量级变化**，但那要重写
`withFileLock` + 全套跨进程回归，需要单独立项。

#### 守卫（`test/fact-reload-signature-2026-10-30.test.js`，7 例）

签名跳过这条路径上出错的后果是"用过期内存储覆盖别人刚写的记忆"——本仓库真发生过同类事故，
所以守卫全打在跨实例/跨径向上：

- 同进程两实例：A 写后 B 必须读到（不许互相覆盖）
- 外部直接改文件后下一次写必须看到（`mtimeNs` 变化能被检出）
- 文件被删后写回，不残留旧内存
- 去重：同内容（含空白/句末标点差异）只留一条并加分
- 去重：不同 `scope` 不互相命中
- 去重：软删后同内容可重新写入；`restore` 后重新回到去重范围

镜像副本 `skills/ppx-memory/scripts/fact-store.js` 同步了全部 8 处改动（漂移守卫 60/60 全绿）。

## 12. 身体批次：给它造痛觉、工作内存和一面镜子（2026-10-30 第五轮）

> §1–§11 全在抠 I/O、token 和并发 —— 都是"能立刻报出数字"的优化。
> 但一个系统最缺的东西往往不是这些：**它不知道自己干得对不对，也没有"手头这件事"的记忆**。
> 这一轮换方向：不优化毫秒，造三样以前没有的东西。

### 12.1 痛觉：`scripts/taskbench-offline.js`

**问题**：`npm test` 有 1845 个断言，但它们只证明"功能没被改坏"；`npm run eval` 是 7 项冒烟
（问候/时间/记忆/文件）。**没有任何东西在量"它能不能把事干成"**，而 `taskbench.js` 要真 LLM key
才能跑 —— 没有 key 的时候，任何优化都只能靠猜（这正是前几轮只能盯着毫秒数的原因）。

更糟的是：`self_improve` / `evolution_loop` 优化的是**测试通过率**，而测试是它自己写的。
没有外部判据的"自我进化"是循环论证。

**做法**（不改既有 taskbench，复用它的资产）：`bench/tasks.js` 里已有 20 个**确定性判分**的任务
（verify 不用 LLM 评审）—— 缺的只是一个执行者。`bench/offline-plans.js` 给每个任务写一份
"人类会怎么走"的工具序列，离线执行器把它当模型的 `tool_calls` 回放，走**真实的** agent 工具循环
（`runToolLoop → _runTool → 沙箱落盘`），最后跑原任务的 verify。

所以它测的是 **harness 能不能把一个正确的计划执行成结果**，不是模型聪不聪明：
路径解析 / 参数校验 / 命令超时 / 结果截断 / 文件落盘 / 记忆写入，任何一环有毛病都会现形。
跑红了是身体的毛病，不是模型的锅。

**首跑就抓到两个真问题**（19/20）：

1. `delete_file` 红。查下去不是删除逻辑错，而是**免疫闸门**拦了：`危险工具未授信: delete_file`。
   而这个错误文案**不可行动** —— 模型不知道能做什么，只会原样重试到轮次耗尽。
   已改成带三条出路（请用户授信 / 换只读方式 / 说明后收尾），与权限引擎拒绝的文案口径对齐。
2. **语义不一致**：`approval_headless = "auto-approve"` 管不到免疫闸门。这是设计（闸门是独立于审批的
   第二道防线），但两套语义没对齐就会让人以为"自动批准了却还是做不了"。基准里改为**对计划中实际
   用到的工具逐个授信**（模拟用户已批准），而不是全局放水 —— 没写进计划的危险工具仍然拦着。

现状：**20/20 通过，3.7 秒**，零 LLM 零网络。这是此后每一轮优化的裁判。

### 12.2 工作内存：`src/session/workstack.js` + `task_stack` 工具

**问题**：每轮 `_context()` 都从人格/画像/技能目录/记忆检索重新拼，拼出来的是「我一贯是谁」和
「你刚才说了什么」—— 中间缺一层：**我正在干什么**。被别的事打断、或上下文被压缩之后回来，
只能靠翻 `memory/turns` 归档去猜"上一件事做到哪了"。

`planning/pwf.js` 是**计划文件**（进 plan 模式才写），这里是**工作内存**（随时可读写，不问模式）。

**契约**：
- 落 `<dataDir>/workstack.json`，原子写 + 文件锁（多进程共享 dataDir 不互相覆盖）；
- 上限 8 条未完成项，超了淘汰最久没动的 —— 栈的意义是"手头"，不是档案；
- 全部步骤勾完自动转 done（省一次显式调用）；
- **渲染段不含时间戳**（逐字节稳定），空栈返回空串（零 token）；
- 段落落在**动态区**（检索段之后）—— 加一件任务不会作废 provider 静态前缀缓存。

### 12.3 记忆质量：`scripts/memory-recall.js`

**问题**：`memory_search` 走 dense+BM25 双路 RRF，dense 那一侧默认是内置 256 维字符 n-gram 哈希向量。
这套"语义检索"的实际能力**从来没被量过**。

**先纠正了自己的口径错误**：第一版直接 `new FactStore()` 测纯 BM25，得出 recall@1 33% ——
但真实链路是 `querySemantic`（plugin 会注入哈希 embedder 再做 RRF）。直接拿纯 BM25 的数字下结论
等于自欺。改成走 `PPXAgent` 的真实装配后：

| 指标 | 纯 BM25（口径错误） | dense+BM25 RRF（真实） |
|---|---|---|
| recall@1 | 33% | **33%** |
| recall@3 | 40% | **60%** |
| MRR | 0.356 | **0.478** |

RRF 确实把 @3 从 40% 拉到 60%，但**仍未及格**：15 个查询里有 6 个连前 3 都进不去，若干查询直接返回空。
典型失败："什么操作系统" → 记忆是"Windows 11"；"怎么防止日志被改" → 记忆是"审计链用 SHA-256"。
字面不重合，哈希向量抓不住，BM25 也没有词可匹配。

这个数字现在的意义：**它是基线，不是一个可以忽略的瑕疵**。要往上走只有两条路 ——
配 `config.embedding` 走真语义模型，或改 RRF 权重/查询扩展。有了这个探针，改动才有裁判。

### 12.4 镜子：身体页（`/api/body.state` + `view-body`）

控制面板此前只有"设置"（旋钮）和"轨迹"（历史），没有一处回答「它现在什么状态、干得好不好」。

侧栏左上角加了一个**身体**入口（带状态点），点进去是四张体征卡：

| 卡 | 数据来源 | unknown 时显示什么 |
|---|---|---|
| 痛觉 · 离线任务成功率 | `data/bench/taskbench-offline-*.json` 最新一份 | "还没跑过: node scripts/taskbench-offline.js" |
| 记忆 · 召回质量 | `data/bench/memory-recall-*.json` + 运行时库规模 | 同上（给命令） |
| 手头的事 · 任务栈 | `agent.workStack.status()` | "手头没挂着的事" |
| 负荷 · 运行时 | 工具数 / 会话数 / provider 数 / 进程 uptime | — |

**关键取舍**：没测过一律 `unknown`（灰点），**不编健康值**。一个会撒谎的仪表盘比没有仪表盘更糟 ——
"没测过"和"测过没问题"必须是两种状态。首屏会静默拉一次，只更新左上角那个点：
打开面板才知道自己健不健康，等于没有仪表盘。

## 13. 身体批次二：让记忆真能听懂人话，把痛觉接进闸门，把数据变成感觉

> §12 建了三样东西（痛觉 / 工作内存 / 镜子），但镜子第一眼照出来的数字是 **记忆召回 60%**，
> 面板上顶着 `overall: "bad"`。这一轮就从这个最差的指标下手，顺带把它变成常驻闸门、把面板做成"身体"。

### 13.1 先承认：之前的"语义检索"根本不是语义

`querySemantic` 是 dense + BM25 两路 RRF。看着像标准做法，但拆开看：

| 路 | 实现 | 本质 |
|---|---|---|
| BM25 | 中文二字组 + IDF 加权 | **字面** |
| dense | 256 维字符 n-gram 哈希向量余弦 | **还是字面**（只是换个加权方式算重合度） |

两路都是"字面重合度"，只是一个按 IDF 排、一个按余弦排。所以 RRF 融合拿不到任何新信息 ——
查询和事实字面零交集时（"什么操作系统" vs "用户用 Windows 11"），两路**同时为空**。

这就是 dev 集 recall@3 卡在 47% 的全部原因。

### 13.2 三个改动，每个都有实测依据

#### ① 留出集：先解决"怎么知道自己没作弊"

优化手段是手工概念词典 —— 这种东西天生过拟合。只有一个查询集时，"调参直到分数变好"
就等于对着考卷改答案。所以先把探针拆成两半：

- **dev（15 查询）**：允许用来设计词典 / 调权重
- **holdout（15 查询）**：**只看不调**，它给的数才叫泛化
- 语料同时扩到 40 条（跨主题，互相干扰），dev 的目标在前 20 条、holdout 在后 20 条

报告里 dev 涨而 holdout 不涨 = 过拟合，不算优化成功，必须重做词典。

#### ② 概念词典（`src/memory/lexicon.js`）：补上唯一能补的那段

零依赖环境下补不了真语义，但能补**中文工作场景的同义/上下位**：40+ 个概念簇，
簇内成员视为"可在检索里互相替换"。命中任意成员 → 整簇参与检索。

写成簇而不是"问题→答案"映射，是刻意的：簇是领域常识（操作系统 = {windows, linux, macos…}），
映射表就只能是背答案。守卫里有一条直接钉住这个形状（`CONCEPT_COUNT >= 30`）。

#### ③ 三路加权融合：dense 的票不该和 BM25 一样重

概念路单独成一路（不拼进查询串），三路 RRF，**但权重不同**：

| 路 | 权重 | 理由 |
|---|---|---|
| BM25 | 1.0 | 字面命中是最可靠的信号 |
| 概念 | 0.9 | 词典受控，但仍是弱证据 |
| dense（哈希） | **0.45** | 字符 n-gram 词袋，噪声大，只在另两路全空时救场 |

`rrfFuse` 原来没有权重参数，三路等权 → dense 的噪声和 BM25 的准确命中**同票**，
融合结果被拉平。加了 `weights`（缺省全 1，向后兼容）后这一项单独贡献了 dev recall@3 从 73% → 93%。

#### ④ dense 准入门槛：0.08 这个数是量出来的，不是拍的

哈希向量给无关中文短句也能算出 0.05~0.07 的余弦。实测 12 组"查询×事实"对：

```
0.275  客户反馈 × 客户投诉要当天回复
0.220  为什么快不起来 × 并发上不去…
0.088  什么操作系统 × 用户用 Windows 11      ← 真命中，但很低
0.074  你在干嘛 × 代码风格统一用两个空格缩进   ← 噪声
0.041  怎么防止日志被改 × 审计链用 SHA-256…   ← 真命中，但被噪声盖过
```

真命中 0.041~0.275，噪声 0~0.074 —— **区间重叠**。阈值取 0.08（而不是我最初写的 0.12）：
0.12 会把 0.088 那条唯一的弱语义桥直接丢掉。margin 很薄，所以配了守卫钉住这两个实测值，
哪天 hash-embedder 改了分词导致分布漂移，测试会红 —— 那正是该重测阈值的信号。

### 13.3 结果

| 集 | 指标 | 改前 | 改后 |
|---|---|---|---|
| **dev**（15 查询，难例） | recall@1 | 33% | **53%** |
| | recall@3 | 47% | **93%** |
| | MRR | 0.417 | **0.700** |
| **holdout**（15 查询，只验收） | recall@1 | 80% | 80% |
| | recall@3 | 87% | **100%** |
| | MRR | 0.850 | **0.889** |
| 总体（30 查询） | recall@3 | 67% | **97%** |

**holdout 也涨了，不是靠 dev 过拟合换来的。** dev 的 recall@1 只到 53% 是诚实的边界：
"怎么防止日志被改" → 需要跨两跳（日志 → 安全 → 哈希/审计），24% 的查询属于这类，
零依赖词典做不对，也不该硬凑。

### 13.4 顺手把它变成闸门（它以前完全没人看着）

`scripts/memory-recall.js --check`：holdout recall@3 < 90% 即非零退出。
门槛按"当前水位的下限"设而不是理想值 —— 它的职责是**拦住回退**（有人改分词/RRF 权重
把召回打回去），不是逼着往上加。

同时 `scripts/taskbench-offline.js --strict` 也进了闸门。`npm run verify` 从 12 项变 **14 项**：

```
✓ 离线任务基准        ← 20 个确定性判分任务走真实工具循环
✓ 记忆召回质量        ← holdout recall@3 ≥ 90%
```

这两条是"痛觉"真正生效的地方。没有它们，两个探针只是脚本；有了它们，退化会在合入前挡住。

### 13.5 皮肤：从"四张指标卡"到"一眼看出哪里不对劲"

面板原来回答的是"数字是多少"，不回答"它现在什么感觉"。三处改动：

**① 躯干 + 器官点，状态靠呼吸节奏**

左侧一个简笔躯干，四个器官对应四项体征（头=痛觉/认知，胸=记忆，腹=负荷，右手=手头的事）。
状态不只靠颜色，还靠**呼吸频率**：ok 慢悠悠 3.4s / warn 1.9s / bad 0.9s + 抖动 /
**unknown 完全不动** —— "不跳"就是"没量过"，比在图上写"暂无数据"更省事也更诚实。
点可点击，亮一下对应卡片（画了空间映射就得让它能用）。

**② 一句话判断 + 体感文案**

顶部从"有指标不健康"这种标签，换成有内容的判断，顺序按医生说话来 ——
先说坏的，再说没测的，最后才报平安：

```
换个说法就找不到记住的东西 —— 这是要修的, 不是要等的。
```

每张卡的主文案不再是 `recall@3 93%`，而是 `15 句换个说法全认得出, 一句没错`。
数字降为小字。判定不变（state 仍由 `toneOfRate` 决定），只换措辞 —— 不洗白任何数字。

**③ 趋势**

原来一天一个 json、当天覆盖，只能看到"最近一次"。新增 `scripts/lib/bench-history.js`
追加 `<kind>-history.jsonl`（保留 60 条），面板读最近 6 次画 sparkline。
**少于 2 个点不画线** —— 一个点连不成线，硬画就是编。

### 13.6 这一轮修掉的三个真实缺陷（都不是新代码引入的）

| # | 缺陷 | 后果 | 怎么发现的 |
|---|---|---|---|
| **D-1** | `.bcards / .bcard / .bdot` 与首页 `#typeCards` **同名** | 身体页的样式把首页类型卡外观改掉了 | 写皮肤时 grep 类名才发现，改为 `.bodywrap` 作用域隔离 |
| **D-2** | 面板用 `recallK`（dev+holdout 混合）当健康值 | 把"泛化能力"和"难例比例"搅在一起，同一份能力在不同 dev 难度下显示不同分 | 换成 `acceptance`（holdout），老报告无此字段时退回 |
| **D-3** | 体感文案分母用了总查询数 30 | 「15 句的 100%」被说成「30 句全对」—— **样本量凭空翻倍** | 复查输出时看到"30 句"与"15 句"矛盾，加守卫钉住 |

另外撞上一个**潜伏的平台相关缺陷**（也顺手修了）：

`public/index.html` 里唯一内联脚本的 sha256 被硬编码在 `SECURITY_CSP` 里，而本机
`core.autocrlf=true`。任何人重新检出把该文件转成 CRLF，哈希立刻失配 → 浏览器**静默**
拦掉首屏主题脚本（页面照常能用，只是主题闪一下，控制台一条 CSP 报错）。

我这次用 Python 写文件时踩了同一个坑（`io.open(p,'w')` 在 Windows 下会把 `\n` 转成 `\r\n`），
全量回归直接红在 `security-headers` 上。修法两层：
- 加 `.gitattributes` 钉死 `public/index.html text eol=lf`（哈希是字节级契约，不许被任何工具改行尾）
- 把本仓库所有被污染的 CRLF 文件统一转回 LF（顺带发现上一轮 8 个文件也是 CRLF）
